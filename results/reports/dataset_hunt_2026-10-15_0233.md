# Dataset hunt: other library checkout data, book sales histories and conversation data on open dataset hosts

Khant Phyo Wai, CMKL University, student ID 01323050, honors thesis
Prepared 15 October 2026. Nothing was downloaded, no account was created and no terms were accepted. Pages were opened in the Browser pane or read through each host's public metadata API (titles, licences, row counts, a two-row sample at most). This report does not repeat `conversation_sources_review.md` (14 October); sources that review already settled (TweetsKB, Bluesky Social Dataset, Podcast Index, Guardian API, Reddit routes, AO3, Stack Exchange) are left out.

## 1. Short answer

Outcomes (what readers do): the hunt found three usable additions and one extension.

1. **South Korea, Library Information Naru (data4library.kr), run by the National Library of Korea.** National and per-library loan counts by book, monthly, with ISBN and subject class. Popular-loan data run from January 2016; per-library files from 2015 or 2018 depending on the library. 1,678 library entries. Licence "attribution (BY)". This is the only other source of loans by title and subject over time that is as long as Seattle's, and it is official.
2. **Edmonton Public Library (Canada), weekly top-10 holds per branch, 2 February 2015 to 18 October 2021.** English, 47,764 rows, 5,585 distinct titles, 22 branches. Open terms (any lawful use).
3. **Brisbane library checkouts 2015 to 2022** (the 2023 to 2025 files are already in the project). Same format, same city, CC BY 4.0. Gives 11 years of sampled days instead of 3.
4. **Monthly format totals** from Timberland Regional Library (2011 to 2026), Norfolk and Mesa: no titles, but print versus digital totals by month.

Interest (what people say): nothing new beats the sources already chosen. Details in section 5.

Dead ends worth knowing about: every other city or country I could find publishes only yearly top-100 lists, branch totals, or very short series (section 4.3). Sales-rank histories exist only as scrapes of Amazon, which break the project's rules.

## 3. Top recommendations, with exact next steps

### 3.1 Korea Data4Library: national popular loans by month and subject class (USE)

Why it fits: it gives a second country's reading outcome by theme, month by month, from 2016. Seattle is one library system in one city; a result that holds in Seoul, Busan and Gyeonggi as well would be much harder to dismiss. Subject class comes with the data (KDC, the Korean Decimal Classification, built on Dewey), so no subject join is needed. Fit: outcome, for replication of the Seattle tests; interest side would be Korean Wikipedia page views (same API the pipeline already uses) and GDELT (it covers Korean news). TweetsKB is English only, so it does not pair with this outcome.

What the page offers (opened 15 October 2026): choose month or year as the period, start date from 1 January 2016 (the date picker's minimum), filters for sex, age band (0 to 5 up to 60 and over), region, subject class (ten main classes, with subdivisions), and result size of 200, 500 or 1,000 books per query. Output is `인기대출도서.csv` or `.xlsx`, or the API `loanItemSrch` with a key. Update cycle is daily. Licence line on the page: 저작자표시(BY). Provider: National Library of Korea.

Limits to keep in mind:
- It is a ranked list (top 200 to 1,000 per query), not every book. Small subject classes will be cut off at the bottom. Use many narrow queries (month by subject subdivision) to reach deeper.
- The API documentation shows no per-ISBN monthly history endpoint, so history is built from monthly ranked lists.
- Korean library loans follow Korean book demand, not English. The thesis' English-first plan stays; this is a replication and a step toward the later Thai work (Asian library data, non-English interest series).

Exact next steps:
1. Khant decides whether to download. Test file first: one CSV for January 2016, monthly, all subject classes, 1,000 rows (about 0.1 to 0.3 MB, estimate). I could not tell if the CSV button needs a login; I did not click it.
2. If bulk work goes ahead, the API route needs a free member account and key (Khant applies; I cannot create accounts). The API page lists no daily limit; the site terms (이용약관) link is script driven and I could not read it, so read it before the first bulk pull.
3. Plan of queries: 130 months (Jan 2016 to Oct 2026) by 10 main subject classes by 1,000 rows is about 1.3 million rows, roughly 100 to 150 MB (estimate), at 1,300 calls or 1,300 CSV exports.
4. Join to titles through ISBN (Open Library and Wikidata, already in the project) only where a book-level interest series is needed; for theme-level work the KDC class is enough.
5. Map KDC classes to the thesis' interest categories with a short table Khant reviews before any test is run.

### 3.2 Korea Data4Library: per-library monthly collection and loan lists (USE, subset)

What it is: for each of 1,678 library entries, one file per month listing the whole holdings that have an ISBN, with loan frequency (page text: "monthly full collection list and loan frequency"). The one I opened for Namsan Library (Seoul education office) is labelled "published from November 2015 to September 2026", 131 files. A small library (Garak Mall) starts in July 2018. Files are text; there is also an API `itemSrch` with library code, start and end date. Licence: BY. Updated monthly (latest 1 October 2026). Some libraries are marked "data no longer published".

Why add it to 3.1: it gives every book's loans, not just the top 1,000, and per-library denominators (holdings). It also removes the censoring problem. The cost is volume and unknowns: file size and exact columns are not shown (a search summary lists title, author, publisher, year, ISBN, KDC, registration date and loan count; check the header of one file). Whether the loan figure is for that month or cumulative is not stated on the page; check on a test file before building anything.

Exact next steps:
1. After 3.1's test file, ask Khant for one more test download: the Namsan file for one month (size unknown; I guess 1 to 10 MB, estimate).
2. Pick 20 to 50 public libraries with the longest history and highest volume (list page `openDataL`, region filter, check the "published from" date on each page).
3. Pull month by month, keep ISBN, KDC, loan count and library code, drop everything else, delete raw files after aggregating.

### 3.3 Edmonton Public Library: weekly top-10 holds by branch, 2015 to 2021 (USE, secondary)

Source: data.edmonton.ca dataset `qdgm-hex6`, provider Edmonton Public Library, page "last updated 11 February 2025", 16,100 views and 1,970 downloads shown (opened 15 October 2026). Content: each Monday-to-Monday week, the ten books with the most holds, for each of 22 customer home branches. Columns: row id, branch code and name, holds, title (text like "The girl on the train / Paula Hawkins"), author, date, link. Checked with the portal's SQL interface: first week 2 February 2015, last week 18 October 2021 (the "updated 2025" is a metadata refresh; the data stop in 2021), 47,764 rows, 5,585 distinct titles.

Fit: outcome, but a different kind: holds are the queue of people waiting, which is demand before the loan. That suits the question (does interest rise before demand rise, and by how many weeks). It overlaps with GDELT (from 2017), Wikipedia page views and TweetsKB (to mid 2023), so about 4.8 years have both sides. It is English and Canadian, so it is an independent replication of Seattle.

Limits: only the top 10 per branch is recorded, so a title appears only when popular; this is selection on the outcome. Use it for "when does a title enter and leave the top list" and for lead-lag around known surges, not for levels. No subject headings: titles and authors must be matched to Open Library or Wikidata (the project already has the match code for Seattle titles).

Terms: City of Edmonton Open Data Terms of Use v2.1 (January 2016, read as PDF): worldwide licence to use, modify and distribute for any lawful purpose including commercial; crediting the City is optional; if the data are passed on, a copy or URL of the terms must go with them. Data are about books, not people (no patron data).

Exact next steps (needs Khant's OK):
1. One request: `https://data.edmonton.ca/resource/qdgm-hex6.csv?$limit=50000`, about 7 MB (estimate), saved to `raw/edmonton_holds_top10.csv` with the terms URL in a text note beside it.
2. Parse "title / author", match to Open Library, report match rate before any test.
3. Build weekly series: number of branches where a title is in the top 10, total holds, first and last week in the list.

### 3.4 Brisbane: extend back from 2023 to 2015 (USE, extension)

Source: data.gov.au pages "Library Checkouts, 2015 to 2019" and "2020 to 2022" (opened 15 October 2026; Brisbane City Council, harvested from Queensland Government open data; both pages say "licence not specified" on data.gov.au, but the Queensland portal's API lists Creative Commons Attribution 4.0 for both). Same fields as the 2023 to 2025 files already in the project (title, author, call number, item identifier, item type, status, language, branch, date borrowed); three-day snapshot each month. The project's existing Brisbane loader and profile show 70 to 79 MB per year for 2023 to 2025.

Fit: outcome, replication on a third library system (Australia), and it brings Brisbane to 11 years, so the Brisbane series covers GDELT's full period and the older Wikipedia data. Limit: three days a month, so it is a monthly sample of days, as before.

Exact next steps (needs Khant's OK): rerun the existing Brisbane script for the dataset slugs `library-checkouts-branch-date-2015-2019` and `library-checkouts-2020-2022` on data.qld.gov.au; expect about 0.5 to 0.65 GB transferred (estimate), keep the same kept columns, delete raw files.

### 3.5 Monthly format totals: Timberland, Norfolk, Mesa (MAYBE, as backdrop only)

- Timberland Regional Library (Washington State; five rural counties): dataset `pz4s-edgu` "Combined Circulation": monthly count by library location and by physical or digital (digital means OverDrive e-books, audiobooks and video). January 2011 to September 2026, 12,665 rows, public domain.
- Norfolk (Virginia): `e68x-a47n`: monthly checkouts by item type and branch, with columns such as adult fiction digital books and adult nonfiction digital books, 2016 to 2026, 1,798 rows, no licence stated.
- Mesa (Arizona): `ujip-2web`: monthly checkouts by branch and material category (physical materials, plus an electronic line), July 2015 to September 2026, 6,285 rows, "see terms of use".

Use: not an outcome for themes (no titles, no subjects). Useful as a control for total demand (COVID closures in 2020, summer peaks, the move from print to digital) so that theme shifts are not read from volume shifts. Cheap: three requests, under 3 MB together. Needs Khant's OK as downloads; I would only do it if the models need such a control.

## 5. Interest side: finding

After searching all hosts above for dated posts, comments, transcripts, news comments or search archives under a research-friendly licence, no dataset beat the sources already chosen (TweetsKB, Wikipedia, GDELT, Tumblr, Stack Exchange, AO3, YouTube API). The reasons, short:
- Reddit copies everywhere trace back to the Pushshift archive; the project excludes it.
- Bluesky and YouTube-Commons copies are too short, too skewed or too large for their gain.
- Search-interest archives are either top-25 lists or are the API application already pending.
- News corpora duplicate GDELT.

Leads I could not verify (listed so you can decide; none opened or tested):
- Media Cloud (mediacloud.org, a university consortium): its home page says it holds over 1 billion stories from over 25,000 sources and has a login; I could not find archive start date, pricing or research terms. A search result says counts through the API need a key, and a 2026 conference paper says the archive passed 1.8 billion stories. Worth a look only if GDELT proves too noisy. It needs an account, which I did not create.
- Apple's chart feeds (Apple Marketing Tools RSS generator, top free and paid books and audiobooks by country): current charts only, no history, terms not read. A daily collector would build a chart history from now on, like the NYT job. Not verified.
- NYT Archive API: the NYT developer site could not be opened by my tools, so I could not read its terms or coverage. Not assessed.
