# Scheduled collectors (run on Khant's Mac by launchd)

These scripts are the source. `jobs/deploy_collectors.sh` copies them (except the one-time `openlibrary_map.py`, which reads the project's data and is run from here) to `~/thesis-collectors` (with its own `.venv`, a copy of `.env` and `secrets/gcp_key.json`, both chmod 600) and loads the launchd schedules in `jobs/launchd/`. They run from outside Documents because macOS blocks background jobs from reading the Documents folder unless a privacy permission is changed. Rerun the deploy script after editing anything here.

| Schedule | What | Limit it respects |
|---|---|---|
| Daily 21:00 (`run_daily.sh`) | `bluesky_sample.py 60`: one hour of public posts; then `nyt_bestsellers.py`: next batch of NYT weeks | NYT 500 calls a day: capped at 480 in any 24 hours (`data/nyt/_calls.json`) |
| Mondays 10:00 (`gdelt_update.py`) | GDELT themes and tone per week, up to the last full week | BigQuery free tier 1 TB a month: free dry run first, 0.9 TB cap, splits across months if needed |
| Daily 09:30, works once a week (`openlibrary_reading_log.py`) | Open Library reading-log counts (want to read, currently reading, already read, stopped reading) for every Open Library work of the study books; weeks run Thursday to Wednesday, first snapshot Thursday 22 Oct 2026 | At most 1 request a second (1.05 s gap), project user agent with contact address; about 6 hours a week |

If the Mac is asleep at the scheduled time, launchd runs the job once when it wakes. Logs: `~/thesis-collectors/logs/`. Data: `~/thesis-collectors/data/`, also visible as `data/collectors/` in the project.

## What is kept
- Bluesky: post time, language and text only. Account IDs, handles, @mentions and links are removed before saving.
- NYT: list name, rank, weeks on list, title, author, ISBN, publisher, description. The overview endpoint has no lists before 2009; those weeks are saved empty.
- GDELT: theme, week, mention count, average tone (overall, positive, negative). Seed range 2017-01-01 to 2021-06-30 is in `data/raw/gdelt_weekly_2017_2021H1.parquet`; the week of 28 Jun 2021 is split across that file and the next one (add mentions, weight tone by mentions when joining).

## Open Library reading log (addendum i, D4_intent_collection)
A weekly history of reading intent for the Test A works (7,747) and the 20,000 Test F books, built from now on. No analysis yet.
- `openlibrary_map.py` (one-time, cached, run from the project: `jobs/bg.sh ol_map ../collectors/openlibrary_map.py --then-snapshot`). Gives each study book one Open Library work: first Wikidata P648 (Open Library ID) of the book's item, or of its edition items; edition IDs (OL...M) are turned into work IDs with `/books/OL...M.json`, and merged works are followed to their new key. Books still without a work: the Open Library search API by the book's ISBNs (Seattle records and Wikidata) and by title and author, then a second search with the title stripped of catalogue extras (', or, ...', '; story and pictures by ...', series forms such as 'Bone. , Eyes of the storm') for books still unmatched. Open Library often has duplicate works for one book; among the candidates that pass the title and author check, the one with the most reading-log entries is kept. Author agreement also uses Open Library's alternative author names (pen names such as M. C. Beaton, filed under Marion Chesney, and other spellings). Every row has its source and a match-quality flag (high, medium, low, none; rules in the script's `decide()`). Wikidata SPARQL: 200 items a query, 2 s apart. Open Library: at most 1 request a second.
- `openlibrary_reading_log.py` (weekly, launchd `com.khant.thesis.openlibrary`). For every mapped work it reads `https://openlibrary.org/works/OL...W/bookshelves.json`, the official endpoint behind the counts on each book page (checked on 3 works on 22 Oct 2026; the counts in the search index lag behind it). launchd starts it every day at 09:30; it only works when this week's snapshot is missing or unfinished, so a run stopped by sleep or a network failure carries on the next day from where it stopped. Each week starts with a batch check of the keys (search API, 100 keys a request) so a work merged since the mapping is read at its new key, since the old key then reads 0. A snapshot still unfinished when the next week starts is saved as `_incomplete`.
- Data (`data/collectors/openlibrary/` in the project, `~/thesis-collectors/data/openlibrary/` on disk): `mapping.parquet` and `mapping.csv` (one row a study book: work_id, testf_id, Test A / Test F flags, Wikidata item, ol_work, source, source_detail, quality, title similarity, author agreement), `mapping_summary.json` (coverage), `map_work/` (caches of the mapping), `snapshots/reading_log_YYYY-MM-DD.csv.gz` (one file a week, named by its Thursday; snapshot_date, ol_work, ol_work_fetched when merged, want_to_read, currently_reading, already_read, stopped_reading, status, fetched_at_utc), `snapshot_log.csv` (one line a week: works, ok, merged, gone, failed, totals, requests, mapping SHA-256). Log: `~/thesis-collectors/logs/openlibrary.log`; the mapping's log is `data/reports/ol_map.log`.
- Only totals per work are requested and kept; no user, list or account data. The two scripts share a lock file, so they never run together and the combined rate stays at 1 request a second. Open Library's robots.txt disallows `/search` for crawlers; `search.json` is the documented API (openlibrary.org/dev/docs/api/search) and is used here only for the one-time mapping and the weekly key check (about 200 requests).
- Mapping made 22 Oct 2026 (about 8 hours over three runs, about 20,000 Open Library requests; `open_library_requests` in the summary counts the last run only): Test A 7,729 of 7,747 books have a work (99.8%; 5,991 through Wikidata P648), Test F 19,292 of 20,000 (96.5%; 4,988 through Wikidata, 14,304 through search); 20,257 different works; quality over the 21,596 books: 20,160 high, 530 medium, 188 low, 718 none. About 900 of the Wikidata work IDs had been merged into other works and were followed. Known limit: about 30 matched titles carry different numbers (series volumes); a few of them are the wrong volume.
- Weekly run time: about 20,300 requests at 1.05 s apart, so about 6 hours while the Mac is awake (on battery with the lid closed the Mac sleeps and the run pauses; it carries on when the Mac wakes, or at the next day's 09:30 start).
- To redo the mapping (for example after adding books), move `mapping.*` and `map_work/` aside and rerun `openlibrary_map.py`; the weekly files keep the old keys, so join each week with the mapping it names (`mapping_sha256` in `snapshot_log.csv`).

## Useful commands
`launchctl print gui/$(id -u)/com.khant.thesis.daily` (state), `launchctl kickstart gui/$(id -u)/com.khant.thesis.daily` (run now), `launchctl bootout gui/$(id -u)/com.khant.thesis.daily` (turn off). The same with `com.khant.thesis.gdelt` and `com.khant.thesis.openlibrary`. The deploy script leaves a schedule that is loaded and unchanged alone, so rerunning it does not stop a collector that is running.

## Privacy
Do not publish the raw Bluesky files. Only aggregated, anonymous results (counts and sentiment by topic and week) go into the thesis. Delete raw social text within three months after the thesis.
